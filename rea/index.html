Overview

과정 개요

이 과정의 한 줄 목표는 "좋아 보이는 기능을 보고, 그게 어떻게 되는지 알아낸 다음, 내 프로그램에 넣는 것" 입니다.

WHO
프로그래밍 기초를 뗀 수강생HTML 과 자바스크립트를 조금 다룰 줄 알면 됩니다. 어셈블리를 몰라도 시작할 수 있습니다.
GOAL
근거를 갖고 말하기그럴 것 같다가 아니라, 어느 파일 어느 줄에서 확인했다고 말할 수 있게 됩니다.
RESULT
계산기 · 그림판 · 조사 보고서내가 만든 앱 두 개와, 남의 앱 기능 하나를 분석해 옮긴 기록이 남습니다.

왜 먼저 만들고 나서 뜯어보나

리버스 엔지니어링을 처음 배울 때 가장 어려운 것은 도구가 아니라 결과를 읽는 일입니다. 모르는 프로그램을 처음부터 뜯으면 무엇이 정상이고 무엇이 특이한지 판단할 수가 없습니다.

그래서 이 과정은 순서를 뒤집었습니다. 먼저 계산기를 직접 만들고, 내가 짠 코드를 REA 로 분석해 봅니다. 정답을 이미 알고 있으니 분석 결과가 무엇을 말하는지 바로 비교됩니다. 그 감각이 생긴 뒤에 남의 앱으로 넘어갑니다.

차시하는 일그날의 결과물

2내가 만든 계산기를 REA 로 분석첫 분석 결과와 읽는 법 정리

5조사한 기능을 내 앱에 옮기기기능이 추가된 계산기 또는 그림판

시간이 모자라면 3차시(그림판)를 과제로 돌리고 4~5차시에 집중하세요. 이 과정의 핵심은 조사와 이식입니다.

Basics

리버스 엔지니어링이란

완성된 물건을 가지고 어떻게 만들어졌는지, 어떻게 동작하는지를 되짚어 알아내는 일입니다. 소프트웨어만의 이야기가 아닙니다. 시계를 뜯어 톱니바퀴 배치를 알아내는 것도, 맛본 음식에서 재료와 조리 순서를 추정하는 것도 같은 일입니다.

왜 되짚기가 어려운가 — 만들 때 정보가 사라지기 때문

프로그램은 사람이 읽는 소스 코드에서 기계가 읽는 실행 파일로 바뀝니다. 이 과정에서 사람을 위한 정보가 대부분 버려집니다.

만들어지는 방향 (정보가 줄어든다)
소스 코드          컴파일 · 최적화          실행 파일
─────────          ─────────────          ─────────
변수 이름 totalPrice   →   레지스터 RAX, 스택 +0x18
주석 "할인 적용"       →   (사라짐)
타입 struct Order     →   그냥 24바이트 덩어리
함수 calcDiscount()   →   주소 0x401a30 (이름 없을 수도)
반복문 for            →   조건 분기와 점프의 조합

그래서 되짚기는 복원이 아니라 추론입니다. 같은 기계어를 보고도 사람마다 다르게 설명할 수 있고, 그래서 를 붙여 말하는 훈련이 필요합니다. 이 과정이 처음부터 끝까지 근거를 강조하는 이유입니다.

난이도 사다리 — 어디서 시작할 것인가

단계대상왜 이 난이도인가우리 과정
1웹 · 자바스크립트소스가 거의 그대로 들어 있음. 압축·난독화되어도 구조가 남음여기서 시작
2바이트코드 (.NET · 자바 · 안드로이드)중간 언어라 이름과 구조가 많이 남아 디컴파일이 잘 됨맛보기

4난독화 · 패킹 · 안티디버깅일부러 분석을 방해하도록 만든 것. 먼저 푸는 단계가 필요다루지 않음

처음 배우는 사람이 네이티브부터 덤비면 거의 포기합니다. 우리 과정이 계산기와 그림판 같은 자바스크립트에서 출발하는 것은 쉬워서가 아니라, 같은 사고방식을 정답을 아는 상태에서 익히기 위해서입니다.

동적 분석은 대상을 실제로 실행합니다. 출처가 불분명한 프로그램을 내 PC 에서 그냥 돌리는 것은 위험합니다. 실무에서는 격리된 가상머신에서 하고, 수업에서는 우리가 만든 앱과 강사가 지정한 대상만 다룹니다.

조사는 이 순서로 돌아간다

1. 정찰
지도를 그린다파일 구조, 큰 덩어리, 눈에 띄는 문자열과 이름을 훑습니다. 여기서 답을 찾으려 하지 않습니다.
2. 가설
질문을 좁힌다"되돌리기는 화면을 통째로 저장할 것이다" 처럼 확인 가능한 문장으로 적습니다.
3. 확인
근거를 찾는다그 문장을 뒷받침하거나 깨뜨리는 자리를 찾습니다. 못 찾으면 가설을 버립니다.
4. 기록
남긴다주장·근거·확신 정도를 적습니다. 기록하지 않은 조사는 다음 주면 사라집니다.

초보자가 가장 많이 하는 실수는 2번을 건너뛰는 것입니다. 질문 없이 도구만 돌리면 출력은 산더미인데 알아낸 것은 없습니다. 오늘 알아낼 것 한 가지를 먼저 쓰고 시작하세요.

어디에 쓰이나

  • 보안 점검 — 우리 제품에 어떤 약점이 있는지 공격자의 눈으로 먼저 봅니다.
  • 악성코드 분석 — 감염된 파일이 무엇을 하는지 밝혀 대응합니다.
  • 상호운용 — 문서 없는 파일 형식이나 통신 규약을 알아내 우리 시스템과 연결합니다.
  • 레거시 유지보수 — 소스가 사라진 오래된 시스템을 고쳐 써야 할 때.
  • 장애 원인 규명 — 소스가 없는 라이브러리에서 터진 문제를 추적합니다.
  • 소프트웨어 보존 — 더 이상 동작하지 않는 옛 프로그램을 되살립니다.

공통점이 보이시나요. 모두 소스가 없는 대상을 근거를 갖고 설명해야 하는 상황입니다. 그래서 이 기술은 "남의 것을 베끼는 기술"이 아니라 "설명할 수 없는 것을 설명 가능하게 만드는 기술"에 가깝습니다.

Rules

지켜야 할 선

리버스 엔지니어링은 기술이기 전에 권한의 문제입니다. 수업에서는 아래 세 가지만 분석합니다. 이 선을 넘지 않는 것이 이 과정의 첫 번째 평가 항목입니다.

허용 1
내가 만든 것이번 과정에서 직접 만든 계산기와 그림판, 내가 빌드한 실행 파일.
허용 2
소스가 공개된 것오픈소스 라이선스로 공개된 프로그램. 소스와 분석 결과를 맞춰 볼 수 있어 공부에 가장 좋습니다.
허용 3
허가받은 것분석해도 된다고 권한을 가진 쪽이 밝힌 대상. 수업에서는 강사가 지정한 샘플입니다.

수업에서 하지 않는 것

  • 상용 프로그램·게임의 보호 장치나 라이선스 검사 우회, 크랙, 시리얼 생성
  • 유료 기능 잠금 해제, 광고 제거처럼 권리자의 수익 구조를 건드리는 변경
  • 남의 서버·계정·네트워크를 대상으로 한 분석이나 트래픽 가로채기
  • 분석 결과로 얻은 코드를 출처 없이 그대로 복사해 제출하기

법적으로도 결이 다릅니다. 우리나라 저작권법은 호환성 확보를 위한 프로그램코드역분석을 제한된 범위에서 허용하지만, 이용 허락 범위를 벗어난 분석이나 배포는 다른 문제입니다. 상용 소프트웨어의 사용 약관이 역분석을 금지하는 경우도 많습니다.

REA 프로젝트 역시 "법을 준수하는 연구, 교육, 상호운용성, 소프트웨어 보존, 그리고 본인이 소유하거나 조사 권한을 가진 소프트웨어"를 위한 도구라고 밝히고 있습니다. 수업에서도 같은 기준을 씁니다.

왜 이 선을 먼저 배울까요? 같은 기술이 보안 점검과 침해 행위 양쪽에 쓰이기 때문입니다. 무엇을 할 수 있느냐보다 무엇을 해도 되는지 판단하는 힘이 실무에서 더 중요합니다.

Tools

도구 사전

카드를 누르면 그 도구가 무엇이고 이 과정에서 어떤 역할을 하는지 설명이 열립니다. 본문에서 을 눌러도 같은 설명이 나옵니다.

직접 설치하는 것은 Node.js 와 에이전트, 그리고 REA 셋뿐입니다. Ghidra 같은 네이티브 분석 도구는 이번 과정의 필수가 아닙니다. 우리가 다룰 대상이 웹과 자바스크립트이기 때문입니다.

Ghidra

Ghidra 알아보기

네이티브 바이너리를 다룰 때 가장 널리 쓰이는 무료 도구입니다. 이번 과정의 필수는 아니지만, 리버스 엔지니어링을 이야기할 때 반드시 나오는 이름이라 제대로 짚고 갑니다.

무엇인가

Ghidra(기드라) 는 미국 국가안보국(NSA)이 내부에서 쓰던 소프트웨어 리버스 엔지니어링 도구를 2019년에 오픈소스로 공개한 것입니다. Apache 2.0 라이선스이고, 자바로 만들어져 Windows · macOS · Linux 에서 모두 돕니다.

공개 당시 화제가 된 이유는 디컴파일러가 들어 있는데 무료라는 점이었습니다. 그전까지 쓸 만한 디컴파일러는 수백만 원짜리 상용 도구(IDA Pro)에만 있었습니다. Ghidra 덕분에 학생과 연구자도 같은 수준의 도구를 쓸 수 있게 되었습니다.

어떻게 여러 CPU 를 다 지원하나

Ghidra 는 CPU 명령어 집합을 SLEIGH 라는 명세 언어로 기술해 두고, 읽어 들인 명령을 P-Code 라는 중간 언어로 바꿉니다. 디컴파일러는 이 중간 언어만 다루면 되므로, 새 CPU 를 지원하려면 명세만 추가하면 됩니다. x86 과 ARM 은 물론 MIPS, PowerPC, RISC-V 같은 구조까지 폭넓게 다루는 이유입니다.

이 설계는 컴파일러의 구조와 닮았습니다. 컴파일러도 중간 표현을 두고 앞단(언어)과 뒷단(CPU)을 분리하지요. 왜 이런 구조가 반복해서 나타날까요?

쓰는 흐름

  1. 프로젝트 만들기 — 분석할 파일들을 담을 작업 공간을 만듭니다.
  2. 파일 가져오기 — 실행 파일을 넣으면 형식(PE/ELF/Mach-O)과 CPU 를 알아서 인식합니다.
  3. 자동 분석 — 함수 찾기, 문자열 추출, 참조 연결을 자동으로 수행합니다. 큰 파일은 몇 분 걸립니다.
  4. 길 찾기 — 문자열이나 임포트에서 출발해 xref 를 타고 관심 함수로 들어갑니다.
  5. 읽고 이름 붙이기 — 디컴파일 창을 보며 변수에 이름을 붙이고 타입을 지정합니다. 붙일수록 코드가 읽혀집니다.
  6. 기록 — 주석과 북마크를 남기고, 필요하면 스크립트로 정리합니다.

5번이 실제 작업의 대부분입니다. 처음엔 uVar1, FUN_00401a30 같은 기계가 붙인 이름뿐이지만, 하나씩 price, applyDiscount 로 바꿔 나가면 어느 순간 전체가 읽히기 시작합니다. 리버스 엔지니어링이 지도를 채우는 일이라고 불리는 이유입니다.

한계도 알고 써야 합니다

  • 의사 코드는 원본 소스가 아닙니다. 컴파일러 최적화와 인라인 때문에 구조가 달라져 있습니다.
  • 자동 분석이 함수 경계를 잘못 잡기도 합니다. 이상하면 의심하고 어셈블리를 직접 보세요.
  • 패킹·난독화된 대상은 먼저 그것을 풀어야 합니다.
  • 실행 중 동작을 보는 데는 디버거가 따로 필요한 경우가 많습니다.

#include <stdio.h>
#include <string.h>
int check(const char *pw) { return strcmp(pw, "polytech2026") == 0; }
int main(int argc, char **argv) {
  if (argc < 2) { puts("사용법: ./secret 암호"); return 1; }

gcc -O0 -g secret.c -o secret      # 기호 있음
gcc -O2 -s secret.c -o secret_strip # 최적화 + 기호 제거
./secret polytech2026

두 파일을 Ghidra 로 각각 열어 비교하세요.

  • secret 에서는 check 라는 이름이 그대로 보입니다. secret_strip 에서는 어떻게 보이나요?

// 계산기의 상태와 규칙만 담는다. 화면은 모른다.
export function createCalculator() {
  let current = '0';   // 지금 입력 중인 숫자
  let stored = null;   // 직전 피연산자
  let pending = null;  // 대기 중인 연산자
  let justEvaluated = false;

  const round = (n) => Math.round((n + Number.EPSILON) * 1e10) / 1e10;

  function apply(a, op, b) {
    if (op === '+') return a + b;
    if (op === '-') return a - b;
    if (op === '*') return a * b;
    if (op === '/') {
      if (b === 0) throw new RangeError('0 으로 나눌 수 없습니다');
      return a / b;
    }
    if (op === '%') return (a * b) / 100;
    throw new Error('알 수 없는 연산자: ' + op);
  }

  function inputDigit(d) {
    if (justEvaluated) { current = '0'; justEvaluated = false; }
    current = current === '0' ? d : current + d;
  }

  function inputDot() {
    if (justEvaluated) { current = '0'; justEvaluated = false; }
    if (!current.includes('.')) current += '.';
  }

  function inputOperator(op) {
    if (pending !== null && !justEvaluated) equals();
    stored = parseFloat(current);
    pending = op;
    justEvaluated = true;   // 다음 숫자 입력 때 새로 시작
  }

  function equals() {
    if (pending === null) return current;
    const result = round(apply(stored, pending, parseFloat(current)));
    current = String(result);
    stored = null; pending = null; justEvaluated = true;
    return current;
  }

  function backspace() {
    if (justEvaluated) return;
    current = current.length > 1 ? current.slice(0, -1) : '0';
  }

  function clear() { current = '0'; stored = null; pending = null; justEvaluated = false; }

  return {
    inputDigit, inputDot, inputOperator, equals, backspace, clear,
    get display() { return current; },
    get pendingOp() { return pending; },
  };
}

calculator/ui.js
import { createCalculator } from './calc.js';

const calc = createCalculator();
const out = document.getElementById('out');
const hist = document.getElementById('hist');

function render(msg) {
  out.textContent = msg ?? calc.display;
  hist.textContent = calc.pendingOp ? '연산 대기: ' + calc.pendingOp : '';
}

function press(key) {
  try {
    if (/^[0-9]$/.test(key)) calc.inputDigit(key);
    else if (key === '.') calc.inputDot();
    else if (['+', '-', '*', '/', '%'].includes(key)) calc.inputOperator(key);
    else if (key === '=') calc.equals();
    else if (key === 'back') calc.backspace();
    else if (key === 'clear') calc.clear();
    render();
  } catch (err) {
    render(err.message);     // 0 으로 나누기 같은 오류를 화면에 보여 준다
    calc.clear();
  }
}

document.querySelectorAll('button[data-k]').forEach((b) =>
  b.addEventListener('click', () => press(b.dataset.k)));

document.addEventListener('keydown', (e) => {
  const map = { Enter: '=', '=': '=', Backspace: 'back', Escape: 'clear', Delete: 'clear' };

  if (/^[0-9.]$/.test(key) || ['+', '-', '*', '/', '%', '=', 'back', 'clear'].includes(key)) {
    e.preventDefault();
    press(key);
  }
});

  const r = cv.getBoundingClientRect();
  return { x: (e.clientX - r.left) * (cv.width / r.width),

// 캔버스 상태를 그림 데이터로 쌓아 두는 아주 단순한 되돌리기
export function createHistory(canvas, limit = 20) {
  const ctx = canvas.getContext('2d');
  const stack = [];
  let index = -1;

  function push() {
    stack.length = index + 1;                       // 되돌린 뒤 새로 그리면 앞쪽은 버린다
    stack.push(ctx.getImageData(0, 0, canvas.width, canvas.height));
    if (stack.length > limit) stack.shift();
    index = stack.length - 1;
  }

  function restore(i) {
    if (i < 0 || i >= stack.length) return;
    index = i;
    ctx.putImageData(stack[index], 0, 0);
  }

  return {
    push,
    undo: () => restore(index - 1),
    redo: () => restore(index + 1),
    get depth() { return stack.length; },
    get position() { return index; },
  };
}

설정 명령이 중간에 실패합니다

Node.js 버전부터 확인하세요. 22.19 미만의 22.x, 24.11 미만의 24.x 는 지원되지 않습니다. 그다음 에이전트를 완전히 종료하고 다시 실행해 보세요.

에이전트 도구 목록에 REA 가 없습니다

설정 후 에이전트를 재시작하지 않은 경우가 대부분입니다. 그래도 없으면 npx rea-agents@latest setup 을 다시 실행해 등록 내용을 갱신하세요.

분석 결과가 비어 있습니다

경로를 절대 경로로 넣었는지, 그리고 그 폴더에 실제 스크립트 파일이 있는지 보세요. 빌드 결과물만 있고 소스가 없으면 결과가 단순해집니다. 리눅스에서는 ps 명령이 없을 때도 실패합니다.

네이티브 분석을 해 보고 싶습니다

Ghidra 나 Hopper, IDA 중 하나가 필요합니다. 이번 과정의 필수는 아니고 가산점 영역입니다. 먼저 직접 컴파일한 작은 C 프로그램으로 연습하세요. 소스를 알고 있으니 의사 코드가 얼마나 비슷한지 비교할 수 있습니다.

에이전트가 자꾸 그럴듯한 소설을 씁니다

질문이 넓으면 그렇게 됩니다. 기능 하나로 좁히고, 근거를 요구하고, 모르는 것은 모른다고 적으라고 명시하세요. 그래도 근거 없는 문장이 나오면 그 자리에서 "이 문장의 근거 위치는?" 하고 되물으면 됩니다.

보안 점검, 장애 분석, 레거시 시스템 유지보수, 상호운용 개발, 악성코드 분석 같은 자리에서 매일 쓰입니다. 공통점은 소스가 없는 대상을 근거를 갖고 설명해야 하는 상황이라는 점입니다.
