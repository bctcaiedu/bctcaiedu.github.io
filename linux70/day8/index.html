Block 1 · 09:00–11:00

격리의 원리

컨테이너는 마법이 아니라 커널 기능의 조합입니다.
첫 번째 블록입니다. 컨테이너를 신비한 기술로 생각하는 분이 많은데, 사실은 리눅스 커널이 원래 갖고 있던 기능 두 가지를 조합한 것입니다. 오늘 그 두 가지를 명령어로 직접 확인합니다.
VM vs Container

가상머신과 무엇이 다른가

가상머신커널까지 통째로하드웨어를 흉내 내고 그 위에 별도의 커널과 OS를 올립니다.

무겁고 부팅에 수십 초. 대신 완전히 다른 OS도 가능합니다.
컨테이너커널은 공유호스트의 커널을 그대로 쓰고 보이는 범위만 나눕니다.

가볍고 기동이 1초 미만. 대신 리눅스 위에서 리눅스만.
Day 1에 만든 VM은 진짜 서버를 흉내 내려고, 오늘의 컨테이너는 환경을 옮기려고 씁니다 — 목적이 다릅니다.
가상머신은 하드웨어를 흉내 내고 그 위에 별도의 커널과 운영체제를 통째로 올립니다. 그래서 무겁고 부팅에 수십 초가 걸립니다. 컨테이너는 호스트의 커널을 그대로 쓰고 보이는 범위만 나눕니다. 그래서 가볍고 일 초도 안 걸려 뜹니다. 대신 리눅스 위에서 리눅스만 돌릴 수 있습니다. 첫날 만든 가상머신은 진짜 서버를 흉내 내려고 쓴 것이고, 오늘의 컨테이너는 환경을 옮기려고 쓰는 것입니다. 목적이 다릅니다.
Namespaces

네임스페이스 — 보이는 범위를 자른다

# 지금 내 셸이 보는 프로세스
$ ps aux | wc -l
142

# PID 네임스페이스를 새로 만들어 들어가 보면
$ sudo unshare --pid --fork --mount-proc ps aux
USER  PID  ... COMMAND
root    1  ... ps aux      ← 자기 자신이 1번입니다
같은 커널, 같은 컴퓨터인데 보이는 세상만 달라졌습니다. 이것이 컨테이너의 절반입니다.
PID·네트워크·마운트·사용자 등 종류별로 네임스페이스가 있습니다.
네임스페이스는 보이는 범위를 자르는 커널 기능입니다. 지금 셸에서 프로세스를 세면 백 개가 넘게 나옵니다. 그런데 언셰어 명령으로 새 피아이디 네임스페이스를 만들어 그 안에서 같은 명령을 실행하면, 자기 자신 하나만 보이고 그것이 일번이 됩니다. 같은 커널, 같은 컴퓨터인데 보이는 세상만 달라진 겁니다. 이것이 컨테이너의 절반입니다.
cgroups

cgroup — 쓸 수 있는 양을 제한한다

$ ls /sys/fs/cgroup/ | head
cpu.max  memory.max  memory.current  pids.max ...

# Docker가 하는 일도 결국 이것입니다
$ docker run --memory=512m --cpus=1 ubuntu ...
네임스페이스무엇이 보이는가 — 프로세스·네트워크·파일시스템
cgroup얼마나 쓸 수 있는가 — CPU·메모리·I/O
컨테이너 = 네임스페이스(격리) + cgroup(제한) + 파일시스템 레이어. 그게 전부입니다.
씨그룹은 자원을 얼마나 쓸 수 있는지 제한하는 기능입니다. 도커에서 메모리 제한 옵션을 주면 결국 이 커널 기능을 설정하는 것입니다. 정리하면 이렇습니다. 네임스페이스가 무엇이 보이는지를 정하고, 씨그룹이 얼마나 쓸 수 있는지를 정하고, 여기에 파일시스템 레이어가 더해지면 그것이 컨테이너입니다. 그게 전부입니다.
Docker basics

이미지와 컨테이너는 다르다

이미지설계도 · 붕어빵 틀읽기 전용. 한 번 만들면 안 바뀝니다.
docker images
컨테이너실행 중인 것 · 붕어빵이미지로 만든 실행 인스턴스. 여러 개 만들 수 있습니다.
docker ps -a
$ docker run -d --name web -p 8080:80 nginx
  -d  백그라운드   --name 이름   -p 호스트:컨테이너 포트 연결
$ docker ps
$ docker logs -f web
$ docker exec -it web bash     # 안으로 들어가 보기
$ docker stop web && docker rm web
이미지와 컨테이너를 구분하는 것이 중요합니다. 이미지는 설계도이고 읽기 전용입니다. 컨테이너는 그 이미지로 만든 실행 중인 인스턴스입니다. 붕어빵 틀과 붕어빵의 관계라고 생각하시면 됩니다. 하나의 이미지로 컨테이너를 여러 개 만들 수 있습니다. 옵션 중 대시 피가 중요한데, 호스트의 포트와 컨테이너 안의 포트를 연결합니다. 이게 없으면 밖에서 접근할 수 없습니다. 도커 이그젝으로 컨테이너 안에 들어가 볼 수 있는데, 들어가 보면 완전히 다른 리눅스처럼 보입니다.
Block 2 · 11:10–12:00

볼륨과 Dockerfile

컨테이너를 지우면 데이터는 어떻게 될까요?
두 번째 블록입니다. 아주 중요한 질문에서 시작합니다. 컨테이너를 지우면 그 안에서 만든 데이터는 어떻게 될까요. 답은 같이 사라진다입니다. 그래서 볼륨이 필요합니다.
Volumes

데이터를 컨테이너 밖에 두기

# 컨테이너 안에 만든 파일은 컨테이너와 함께 사라집니다
$ docker run --rm ubuntu bash -c "echo hi > /tmp/a.txt; cat /tmp/a.txt"

# 볼륨: Docker가 관리하는 저장소
$ docker volume create mydata
$ docker run -v mydata:/data ubuntu bash -c "echo hi > /data/a.txt"
$ docker run -v mydata:/data ubuntu cat /data/a.txt   ← 남아 있습니다

# 바인드 마운트: 내 디렉터리를 그대로 연결
$ docker run -v ~/ai-lab/datasets:/data ubuntu ls /data
모델 캐시는 반드시 볼륨에 둡니다 — 컨테이너를 지울 때마다 수 GB를 다시 받을 수는 없습니다.
컨테이너 안에 만든 파일은 컨테이너를 지우면 함께 사라집니다. 그래서 남겨야 할 데이터는 밖에 둡니다. 두 가지 방법이 있습니다. 볼륨은 도커가 관리하는 저장소이고, 바인드 마운트는 내 컴퓨터의 디렉터리를 컨테이너 안에 그대로 연결하는 것입니다. 오늘 실습에서 모델 캐시를 반드시 볼륨에 둘 텐데, 이유는 명확합니다. 컨테이너를 지울 때마다 수 기가바이트짜리 모델을 다시 받을 수는 없기 때문입니다.
Dockerfile

이미지를 코드로 만들기

FROM python:3.12-slim          # 기반 이미지
WORKDIR /app

COPY requirements.txt .        # ① 의존성 파일만 먼저
RUN pip install --no-cache-dir -r requirements.txt

COPY . .                        # ② 소스는 나중에
ENV OLLAMA_HOST=http://ollama:11434
CMD ["python", "client.py"]
①과 ②의 순서가 핵심입니다. 소스만 고쳤을 때 pip install을 다시 하지 않게 됩니다.
각 줄이 하나의 레이어입니다. 바뀐 줄부터 아래만 다시 만들어집니다.
도커파일은 이미지를 만드는 설명서입니다. 여기서 오늘 가장 실용적인 지식이 나옵니다. 각 줄이 하나의 레이어가 되는데, 도커는 바뀌지 않은 레이어를 재사용합니다. 그래서 의존성 파일을 먼저 복사해서 설치하고, 소스 코드는 나중에 복사해야 합니다. 이 순서를 지키면 소스만 고쳤을 때 핍 인스톨을 다시 하지 않습니다. 순서를 반대로 하면 한 글자만 고쳐도 매번 몇 분씩 기다려야 합니다. 오후 실습에서 이걸 직접 측정해 봅니다.
compose

compose — 여러 서비스를 한 파일로

# compose.yaml
services:
  ollama:
    image: ollama/ollama
    volumes: [ollama_models:/root/.ollama]
    ports: ["11434:11434"]
    restart: unless-stopped

  webui:
    image: ghcr.io/open-webui/open-webui:main
    ports: ["3000:8080"]
    environment:
      - OLLAMA_BASE_URL=http://ollama:11434
    depends_on: [ollama]

volumes:
  ollama_models:
같은 compose 네트워크 안에서는 서비스 이름이 곧 호스트 이름입니다.
docker compose up -d 한 줄로 전부 뜨고, down -v 한 줄로 전부 사라집니다.
컴포즈는 여러 서비스를 한 파일에 적어 두고 한 번에 띄우는 도구입니다. 여기서 중요한 것이 하나 있습니다. 같은 컴포즈 네트워크 안에서는 서비스 이름이 곧 호스트 이름이 됩니다. 웹 유아이가 올라마에 접근할 때 아이피가 아니라 올라마라는 이름으로 부를 수 있습니다. 컴포즈 업 대시 디 한 줄로 전부 뜨고, 다운 대시 브이 한 줄로 전부 사라집니다. 이 지우고 되살리는 사이클이 오늘의 마지막 검증입니다.
GPU

GPU 컨테이너는 한 겹 더

# 호스트에 드라이버 + nvidia-container-toolkit 설치 후
$ docker run --rm --gpus all nvidia/cuda:12.4.0-base nvidia-smi

# compose 에서
    deploy:
      resources:
        reservations:
          devices:
            - capabilities: [gpu]
드라이버는 호스트에, CUDA 런타임은 이미지에 — 이 구분이 GPU 컨테이너 오류의 대부분입니다.
GPU가 없는 환경에서는 개념만 보고 넘어갑니다. CPU로 오늘 실습은 전부 됩니다.
지피유를 컨테이너에서 쓰려면 한 겹이 더 필요합니다. 엔비디아 컨테이너 툴킷이라는 것을 호스트에 설치해야 컨테이너가 지피유를 볼 수 있습니다. 여기서 헷갈리기 쉬운 구분이 있습니다. 드라이버는 호스트에 있어야 하고, 쿠다 런타임은 이미지 안에 있어야 합니다. 어제 본 층 구조가 컨테이너에서는 이렇게 나뉩니다. 지피유 컨테이너 오류의 대부분이 이 구분을 몰라서 생깁니다.
