1부 · L01~L05

Git 기초

버전 관리가 무엇인지, 커밋 하나가 만들어지기까지. 그리고 실수했을 때 되돌리는 법.

🌱

교수 노트

  • 1부의 목표는 "막히면 git status 부터" 라는 습관입니다. 출력의 괄호 안 안내를 소리 내어 읽게 하세요.
L01 · L02 · 버전 관리와 첫 커밋

작업 폴더 → 스테이징 → 저장소

  • Git 은 내 컴퓨터의 프로그램, GitHub 은 저장소를 올려 두는 웹 서비스
  • 분산 방식 — 모든 이력이 내 컴퓨터에, 인터넷 없이도 커밋
  • 커밋 = 그 순간의 스냅숏, 커밋 ID = 내용으로 계산한 해시
  • 처음 한 번: git config --global user.name · user.email
git init
git status
git add index.html        # 담기 (스테이징)
git commit -m "첫 커밋"    # 남기기
git log --oneline
스테이징은 장바구니고친 것 중 이번 커밋에 넣을 것만 골라 담습니다.

교수 노트 · 80분

  • 미션 "커밋이 거절된 까닭 찾기"는 이름 · 메일 설정을 안 했을 때의 오류입니다. 실제 PC 에서도 가장 먼저 만나는 오류입니다.
  • "두 파일 가운데 하나만 커밋하기"로 스테이징이 왜 있는지 직접 느끼게 합니다.
L03 · 변경 살펴보기

diff · log · show · blame

git diffadd 하지 않은 변경
git diff --staged커밋에 들어갈 변경
git diff HEAD마지막 커밋 뒤 모든 변경
git log --oneline -n 5 --stat이력 찾기 (--author · --grep · 경로)
git show · git blame커밋 하나 · 줄마다의 내력
좋은 커밋 메시지
제목 = 무엇을, 본문 = 왜제목은 50자 안쪽. "수정" 대신 "영업 시간을 9시로 바꿈"
작은 커밋
일 하나에 커밋 하나섞인 변경은 git add -p 나 파일별 add 로 둘로 나눕니다

교수 노트 · 45분

  • diff 의 - · + · @@ 를 화면에서 손가락으로 짚어 가며 읽어 줍니다. 미션 "잘못된 영업 시간이 들어온 커밋 찾기"는 log -p · blame 연습입니다.
L04 · 되돌리기

실수가 어디까지 갔나로 고른다

실수가 있는 곳명령결과
작업 폴더git restore 파일고친 것을 버림 (되찾을 수 없음)
스테이징git restore --staged 파일담은 것만 취소
방금 커밋 (push 전)git commit --amend마지막 커밋을 새 커밋으로 (ID 바뀜)
여러 커밋 (push 전)git reset --soft / --mixed / --hard커밋만 / 스테이징까지 / 작업 폴더까지
이미 push 함git revert 커밋취소하는 커밋을 새로 만듦
구명조끼 — git reflog커밋한 적이 있는 것은 reset --hard 로 날려도 reflog 에서 되찾습니다. 커밋하지 않고 버린 것은 못 찾습니다.

교수 노트 · 50분

  • 가장 중요한 원칙: 공유한 커밋은 revert, 공유하지 않은 커밋은 reset/amend. P5 사고 복구 훈련에서 다시 나옵니다.
L05 · 파일 관리와 .gitignore

올리지 않을 파일 정하기

# .gitignore
.env              # 비밀 값
*.log             # 확장자
build/            # 폴더
node_modules/
!keep.log         # 예외
/temp.txt         # 맨 위 폴더만
**/cache/         # 모든 깊이
  • git rm · git mv — 지우고 옮기면서 스테이징까지
  • 이미 추적 중인 파일은 git rm --cached 로 먼저 빼야 무시됨
  • git clean -n 으로 확인 → -f 로 지움 (되찾을 수 없음)
비밀 값을 올렸다면파일을 지워도 이력에 남습니다. 키부터 바꿉니다 (L21).

교수 노트 · 45분

  • 미션 "실수로 커밋한 .env 를 추적에서 빼고 무시하기"는 AIoT · Docker 과정의 .env 관리와 똑같습니다.
2부 · L06~L10

브랜치

갈라졌다 합치기, 충돌 풀기, 이력 다듬기, 하던 일 치워 두기와 버전 이름표.

🌿

교수 노트

  • 강좌의 커밋 그래프 그림을 계속 띄워 두고 "이름표가 어디로 움직였나"만 묻습니다. 브랜치 = 이름표라는 그림이 잡히면 2부가 쉬워집니다.
L06 · L07 · 브랜치와 병합

브랜치는 이름표, 병합은 줄기 합치기

  • 브랜치 = 커밋 하나를 가리키는 이름표. 만들어도 커밋은 늘지 않음
  • HEAD = 지금 서 있는 브랜치. 새 커밋은 그 브랜치에
  • git switch -c 이름 만들며 옮기기, branch -d / -D
  • 분리된 HEAD 의 커밋은 switch -c 로 이름표를 붙여 지킴
병합언제 · 결과
빨리 감기받는 쪽에 새 커밋 없음 → 이름표만 이동
3-way양쪽에 새 커밋 → 부모 둘인 병합 커밋
--no-ff늘 병합 커밋 남기기
--squash커밋 하나로 뭉쳐 가져오기
--abort병합 시작 전으로

교수 노트 · 100분

  • 병합은 받는 쪽에 서서 git merge 가져올브랜치. 반대로 서서 병합하는 실수가 가장 많습니다.
L08 · 충돌 해결

충돌은 고장이 아니라 질문

<<<<<<< HEAD
영업 시간: 오전 9시   # 내 쪽
=======
영업 시간: 오전 10시  # 가져오는 쪽
>>>>>>> feature
  1. 표시 줄을 지우고 남길 내용으로 고치기
  2. git add 파일 (해결 표시)
  3. git commit 으로 병합 끝내기

checkout --ours / --theirs 한쪽 통째로 · 수정/삭제 충돌은 add(남김) 또는 rm(지움)

교수 노트 · 50분

  • 미션 "충돌 표시가 든 채 커밋된 파일 바로잡기"는 실제로 자주 일어납니다. grep -n "<<<<<<<" 로 찾는 습관을 알려 줍니다.
L09 · L10 · rebase · stash · tag

이력 다듬기와 버전 이름표

rebase
새 밑동 위에 다시 쌓기이력이 한 줄, 커밋 ID 가 바뀜. 공유한 커밋은 rebase 금지. -i 로 pick · squash · fixup · drop
stash
하던 일 선반에 올리기급한 수정: stash → main 에서 수정 → 병합 → 돌아와 pop. -u 새 파일까지
tag
움직이지 않는 이름표배포 판은 git tag -a v1.0.0 -m "…", 올리기는 따로 git push origin v1.0.0

git cherry-pick 커밋 커밋 하나만 가져오기 · 버전은 MAJOR.MINOR.PATCH · git describe 가장 가까운 태그로 설명

교수 노트 · 110분

  • rebase 중 충돌: 고치기 → add → git rebase --continue (commit 이 아님). 그만두려면 --abort.
3부 · L11~L13

GitHub 와 원격 저장소

내 컴퓨터의 저장소를 GitHub 과 주고받기. push 가 거절될 때 당황하지 않기.

🐙

교수 노트

  • 여기서부터 실제 GitHub 연결을 권합니다. 토큰은 실습 저장소 권한만, 짧은 만료로 만들고 수업 뒤 삭제하게 합니다(L11 · L21).
L11 · L12 · push · clone · fetch · pull

origin 과 origin/main

git remote add origin https://github.com/나/repo.git
git push -u origin main   # -u: 업스트림 정하기
git push                  # 그다음부터

# 한 번에
gh repo create repo --public --source=. --push

origin = 원격 주소의 별명, git remote -v 로 확인

git clone 주소이력 전체 + origin 등록 + 업스트림
git fetch받아 오기만 (origin/main 이동)
git pullfetch + 병합
ahead · behind올릴 커밋 · 받을 커밋 수
git log main..origin/main합치기 전에 받을 커밋 보기
git fetch --prune지워진 원격 브랜치 표시 정리

교수 노트 · 100분

  • origin/main 은 "마지막으로 확인한 원격 main" 이지 원격 그 자체가 아니라는 점 — fetch 해야 움직입니다.
L13 · 함께 쓰는 원격 저장소

push 가 거절될 때

 ! [rejected]  main -> main (fetch first)
error: failed to push some refs
  1. 원격에 내가 합치지 않은 커밋이 있다는 뜻
  2. git pull — 갈라졌으면 --no-rebase · --rebase · --ff-only 중 고르기
  3. 충돌은 병합 충돌과 똑같이 풀기
  4. 다시 git push
공유 브랜치에 강제 push 금지혼자 쓰는 브랜치에서 꼭 필요하면 --force-with-lease. 새 브랜치는 push -u origin 브랜치, 지우기는 push origin --delete 브랜치.

교수 노트 · 60분

  • 두 학생이 같은 저장소에 동시에 push 하게 해서 거절을 직접 만들어 보면 이해가 빠릅니다(실제 GitHub 연결 시).

L14 · L15 · 이슈와 풀 리퀘스트

GitHub Flow

  1. 이슈 만들기 gh issue create
  2. 브랜치 switch -c fix-hours
  3. 커밋 · push
  4. PR 열기 gh pr create
  5. 리뷰 · 토론 · 갱신
  6. 병합 · 브랜치 삭제
Fixes #3 · Closes #3기본 브랜치에 들어갈 때 이슈가 닫힘
병합 방식병합 커밋(--merge) · 스쿼시(--squash) · 리베이스(--rebase) — 이력 모양이 다름
PR 갱신같은 브랜치에 push 하면 PR 이 따라서 바뀜
초안--draft 로 열고 준비되면 gh pr ready

교수 노트 · 110분

  • 좋은 이슈 = 분명한 제목 · 재현 방법 · 기대 결과 · 실제 결과. AIoT 팀 프로젝트의 할 일도 이 형식으로 이슈에 적게 합니다.
L16 · L17 · 리뷰 · 보호 · 포크

main 을 지키고, 남의 저장소에 기여하기

  • 리뷰 세 가지: Comment · Approve · Request changes (자기 PR 은 승인 불가)
  • gh pr checkout 번호 로 받아 직접 확인
  • PR 의 충돌은 내 브랜치에서 main 을 병합해 풀고 push
  • 브랜치 보호 — 직접 push 금지, 승인 · 검사 필수. 어기면 GH006
포크
origin = 내 포크, upstream = 원본포크 → 복제 → 브랜치 → 커밋 → 내 포크에 push → 원본에 PR
git fetch upstream
git merge upstream/main
git push origin main   # 포크를 원본과 맞추기

교수 노트 · 115분

  • 권한 없는 저장소에 push 하면 403 — "포크가 답"이라는 흐름을 미션 "포크 없이 복제한 저장소에서 한 작업 살리기"로 확인합니다.

L18 · GitHub Actions 기초

push 할 때마다 GitHub 이 대신 검사

# .github/workflows/check.yml
name: Check
on:
  push:
    branches: [main]
  pull_request:
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: test -f README.md
  • on 언제 · jobs 무엇을 · steps 어떤 순서로
  • queued → in_progress → completed, gh run watch
  • 실패하면 gh run view --log-failed → 고친 커밋 push
  • PR 검사는 gh pr checks
  • 비밀 값은 ${{ secrets.이름 }}

교수 노트 · 60분

  • 가상 GitHub 은 워크플로를 흉내 내어 실행합니다(echo · test · cat 등). 실제 GitHub 연결 시에는 진짜 러너가 돕니다.
L19 · GitHub Pages 로 사이트 배포하기

저장소의 파일이 그대로 웹 사이트로

주소: https://{user}.github.io/{repo}/ · 첫 화면 index.html

  1. index.html · style.css 커밋 · push
  2. Settings → Pages → Deploy from a branch → main · / (root) 또는 /docs
  3. 한 번 켜 두면 push 할 때마다 사이트가 바뀜
HTML 경로결과
href="style.css"열림 (권장)
href="/style.css"404 — 저장소 이름이 빠짐
404 점검 순서Pages 켜짐? → 브랜치 · 폴더? → index.html 이름 · 대소문자? → push 했나?

permissions:
  contents: read
  pages: write          # Pages 에 쓸 권한
  id-token: write       # 신분 증명 토큰
jobs:
  build:
    steps:
      - uses: actions/checkout@v4
      - run: test -f site/index.html   # 배포 전 검사
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with: { path: site }
  deploy:
    needs: build
    environment: github-pages
    steps:
      - uses: actions/deploy-pages@v4

QUIZ

확인 퀴즈 클릭하면 정답

  1. 이미 push 한 잘못된 커밋을 취소하려면?
    → git revert 커밋. 공유한 이력은 reset 으로 고쳐 쓰지 않습니다.
  2. push 가 ! [rejected] (fetch first) 로 거절됐다. 무슨 뜻이고 어떻게?
    → 원격에 내가 합치지 않은 커밋이 있음. git pull 로 받아 합친 뒤 다시 push.
  3. 프로젝트 사이트에서 <link href="/style.css"> 는?
    → 저장소 이름이 빠진 주소를 찾아 404. 상대 경로 style.css 로.
  4. 사이트 파일이 dist 폴더에 생긴다. Pages 로 배포하려면?
    → GitHub Actions 방식, upload-pages-artifact 의 path: dist (브랜치 방식은 / · /docs 만).
  5. Pages 배포 워크플로에 꼭 필요한 권한 두 가지는?
    → pages: write, id-token: write
